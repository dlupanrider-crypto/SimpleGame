# 平安同行：准点撤离设计

> 实施状态：首版草稿已可试玩，本文是目标设计，实际完成范围和差异以 [执行计划](PLAN.md) 为准。

特性 ID：`pingan-monopoly`  
状态：`active`，首版开发中  
更新：2026-10-29（Asia/Shanghai）  
适用项目：午间俱乐部 Chrome 扩展

详细地图见 [长局地图设计](MAP_DESIGN.md)，事件和状态机见 [首版玩法规格](GAMEPLAY_SPEC.md)。文档均为待评审提案。

## 1. 核心主线

**在到点下班的那一刻，不被领导或同事发现，成功离开工位并抵达电梯或出口。**

将本来正常的准点下班，戏剧化为一场轻松的办公室潜行任务。玩家要规划路线，避开领导办公室、同事工位、茶水间等高危区域；被叫住对方案、安排任务或拉去开会则返回工位，本局撤离失败。隐藏目标是保持体面：既不显得心虚，也不张扬。

名称暂定「平安同行：准点撤离」。继续保留大富翁式棋盘、掷骰、路线和事件卡，但**胜负由撤离结果决定**。先前的地产购买、收租、成长值和资产排名方案取消；此前仅有设计，没有已发布的旧版本。使用的地点、人物和职场梗都是虚构讽刺，不代表真实公司制度或员工经历。

首版目标：固定 4 个玩家席位（1～4 名真人，不足由机器人补足），默认 40 轮上限，目标支持 30 轮以上，实际时长待测试；具体节奏与参数均为设计草案，需通过测试和用户验收调整。

## 2. 多人目标与结算

- 玩家均从自己的工位出发，轮流行动；本局各自独立逃离，先成功不会结束其他人的回合。
- **成功**：在回合限制内走到电梯或出口，且没有触发被叫住；成功后离场并观战。
- **失败**：触发被叫住、临时任务、会议或被发现，立即返回起始工位并结束个人行动；到达限制时仍未撤离也判失败。失败玩家可观战，不再行动。
- 本局默认 40 轮上限；一轮是所有仍在行动的玩家各执行一次回合。全部玩家成功或失败时提前结算。
- 排名先按成功、失败分组；成功者按完成回合较早优先，同回合则按体面值较高优先，仍相同为并列。失败者不按玩家 ID 硬排，显示失败原因。
- **隐藏目标**：体面值不是进入出口的硬性条件，也不否定撤离成功；仅在结果中展示「从容离场」等评价及同回合排名。界面可显示行为反馈，避免把隐藏目标做成不可解释的惩罚。

## 3. 地图与路线

首版拟采用三层、每层 7×7 的可分岔办公室网格，详见 [地图设计](MAP_DESIGN.md)；最终美术待验收。地点包括起始工位、开放办公区、同事工位、茶水间、会议室、领导办公室门口、安静走廊、电梯和出口。节点之间由可走通道明确连接；边界、墙和不可达节点在玩法包中定义，客户端显示可走路径。

高危地点有可见提示与不同风险；同事工位可能触发“对一下方案”，领导办公室门口可能触发“就五分钟”，会议室附近可能被临时拉会。玩家可选较短但高风险的路线，或绕走安静区域；不是单一路径的随机前进。初始地图必须至少有两条从工位到出口的可达路线，并有明确电梯和出口终点。

展示上采用虚构的俯视办公室：玩家棋子、墙体、风险区域和终点均可辨认；不能仅凭颜色区分状态。使用现有浅色卡片风格与平安橙点缀，实际品牌标识仍待规范确认。

## 4. 回合、风险和体面

以下参数为首版可测试方案，发布前根据实测调整并冻结到对应版本：

1. 当前玩家掷一个六面骰，1～3 为 1 步、4～6 为最多 2 步；可在这个上限内选择至少一步的相邻合法路径，并可提前停下。不可越墙、越界，已到达终点立即停止移动。
2. 逐格移动并检查经过格的风险；高危节点增加 1 点“被发现风险”，安全节点不增加。落点再触发相应事件；事件的移动使用同样路径合法性和经过风险规则，且每次行动最多额外触发一次落点事件，防止连锁死循环。
3. 被发现风险为 0～4，达到 4 立即判定被发现、返回工位并失败；强制失败事件也立即判失败。结算顺序固定为：进入节点、累积风险并检查失败、到终点则成功，否则处理落点事件。
4. 每人初始体面值 3，范围 0～5；明目张胆或过度心虚的选择降低体面，平静自然或合理协作可提高体面。体面变化要显示原因，数值不会隐式改变风险或直接触发失败。
5. 界面显示剩余步数、当前位置、下一步可选节点、路径风险提示、事件效果和结果。事件选择由当前玩家完成；服务器端不存在，规则由房主端裁定并广播。

玩家可以停在安全位置等待下一轮，但不能原地跳过行动。若行动规则需要允许等待，必须作为新版本明确规定。

## 5. 热梗、事件与选择

至少 30 张经审核的可玩事件，分别覆盖职场日常、网络热梗、黑话翻译、画饼/甩锅讽刺和队友互动。事件牌堆洗牌后依次抽取，耗尽后重新洗牌；事件可按区域、行动阶段和内容开关过滤。文案引用用户提供的 [76 条可版本化素材草稿](content/workplace-humor.zh-CN.0.1.0-draft.json)，素材与事件效果分开，不能将素材数量说成已实现事件数量。

| 事件 | 情境及选择 | 效果草案 |
| --- | --- | --- |
| 就五分钟 | 领导邀请你临时对方案 | 被叫住，返回工位并失败 |
| 这就拉个群 | 临时会议消息传来 | 被拉会，返回工位并失败 |
| 卡急马 | 临近下班，包已背好 | 选择自然整理：体面 +1；急冲出口：体面 -1、风险 +1 |
| 背手负鼠 | 内心慌张，表面镇定 | 体面 +1，移动在当前位置结束 |
| 班味入骨 | 打工气息暴露了疲惫 | 风险 +1 |
| 工位坐禅 | 同事短暂放空 | 风险 -1，最低为 0 |
| 高效对齐 | 将模糊黑话翻译成人话 | 答对风险 -1；跳过或答错无额外处罚 |
| 跨团队神助攻 | 队友帮忙转移注意力 | 选择一位仍在行动的其他玩家，其风险 -1；无人可选时自己风险 -1 |
| 需求临时调整 | 任务被安排到当前玩家 | 返回工位并失败 |

事件示例为设计草案，不代表已经实现。游戏应在确认前展示选择可能造成的效果，不以不明确的文案暗扣状态。涉及其他玩家的事件不泄露隐私，不生成冒充玩家发送的聊天内容；敏感或较尖锐的吐槽默认关闭，房主在建房时选择。

## 6. 创建、房间与界面

大厅游戏卡进入创建房间；填写房名、选择玩法版本、选择是否启用较尖锐内容。创建时明确显示人数、地图、限制轮数、预计时长和规则。房间列表、邀请及房间顶部显示名称、版本号、内容模式和参与人数。

房间主区域展示办公室地图、当前角色和路径；右侧展示玩家状态、回合和最近事件。当前玩家的操作提示包含“选择路径 / 确认移动 / 处理事件”，非当前玩家显示等待；结算页区分成功与失败原因，并展示体面评价。移动端棋盘允许缩放或滚动，动作和风险信息不能被遮住。

## 7. 可扩展版本

新首版提案为 `office-escape@1.0.0`，名称「准点撤离·轻量版」。它与之前未实现的 `workplace-lite@1.0.0` 是不同玩法，不能复用旧 ID 或把旧规则伪装为新版本。之前方案仅作设计历史，不作为可选择的已发布版本。

每个不可变玩法包包含：地图与通道、规则参数、事件与效果、素材包版本和内容哈希、界面信息以及所需引擎协议版本。包以确定性序列化计算 SHA-256，内容更改必须新版本；哈希用于检测一致性，不代表签名或信任。

房主建房时选择版本及内容模式，房间公告和邀请携带玩法 ID、版本、协议和内容哈希；接收方在接受和开局前校验本地包。缺失、不一致或不兼容时显示原因并拒绝进入，不能静默降级。对局开始后冻结配置，已安装的新版本不改变进行中的对局。保留已发布旧版，未来可选择“更多路线”“团队协作”等独立版本；具体新版本不在首版预先承诺。

现有扩展没有服务端，也没有内容自动分发；玩法包随扩展发布，双方须安装包含相同包的扩展。旧插件未实现兼容协议，如何可靠提示旧客户端须在实现时验证，不能假设旧客户端会主动拒绝。恢复房间需先检查原包可用性，不可用时告知用户，不替换版本。

## 8. 联机及断线

复用现有大厅与加密游戏通道，房主维护唯一权威状态：玩家位置、路径、风险、体面、状态、事件牌堆、行动序号及当前阶段。客户端提交动作；房主验证玩家身份、当前回合、合法相邻路径、步数、事件选择、版本及对局 ID，再广播结果。重复、过期或乱序消息不能重复结算。随机数由房主产生，其他玩家无法独立证明公平；房主可以通过开发工具修改状态。

机器人由房主在本地控制，按同样的阶段和规则行动，参与结算并明显标注身份；补位和机器人行动的随机结果由房主同步。机器人策略优先合法路径、避免已知危险，不读取隐藏牌堆或预知骰子，具体策略与动画时间在实施时验证。真人掉线不自动替换为机器人。

非房主离线时暂停该玩家回合，房主可选择等待或确认将该玩家判为退出；具体等待和重连流程须在实现时验证现有传输能力，不假定自动重连。房主关闭页面时当前对局断开；首版不承诺房主迁移或恢复未完成棋局。已保存房间的版本信息可用于重新开始。

## 9. 实施和验收

实施时将特性目录整体移入 `features/active/`，记录计划、测试与用户验收；只有全部必需验收完成后才能归档。验收至少包括：

- 地图连通性、不同路线与风险、骰子、合法/非法路径、终点与风险结算顺序。
- 被叫住、任务、会议立即失败返回工位；成功玩家不影响其他玩家；40 轮超时、全部结算、体面评价与并列。
- 事件选择、热梗内容开关、黑话题答案、牌堆去重、事件移动与连锁上限。
- 包版本选择、哈希不一致、兼容失败、旧包共存、对局快照冻结；重复及非法消息不影响状态。
- 断线等待与退出、房主离开、玩家重连边界；各屏宽地图可读，键盘操作可达。
- 真实浏览器和至少两台设备的邀请、同步及网络中断实测；事件措辞、平衡和体验由用户验收。
